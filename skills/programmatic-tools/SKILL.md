# Programmatic Tool Calling（程序化工具调用）

> 核心理念：**用代码编排工具，而不是用对话编排工具。**
> 
> 当任务需要多步数据转换时，写一段脚本在本地执行，只把最终结果放入上下文。

---

## 什么时候用 PTC？

**推荐使用脚本的情况（满足任一即可）：**

1. **批量文件扫描**：涉及 3 个以上文件的读取、解析或比较。
2. **数据转换**：JSON/YAML/CSV 的提取、过滤、聚合、排序、去重。
3. **数学/统计计算**：求和、平均值、分布统计、正则匹配计数。
4. **格式规范化**：批量重命名、批量生成报告表格、批量验证。
5. **中间结果庞大**：单步工具调用会产生大量冗余文本进入 context。

**不推荐用脚本的情况：**

1. **单文件简单查看**：直接用 `ReadFile` 或 `bat` 更高效。
2. **需要人工逐步确认**：如删除重要文件、修改系统配置，应分步执行并逐条确认。
3. **脚本复杂度超过 50 行**：应考虑拆分成多个小脚本，或回到分步工具调用。

## 执行协议（安全优先）

### Step 1: 意图声明
在写脚本前，用一句话说明：
- 脚本要做什么
- 预计读取/修改哪些路径
- 为什么用脚本比单步工具更高效

### Step 2: 脚本审查
将脚本完整展示给用户，并标注风险等级：

| 风险等级 | 判定标准 | 处理方式 |
|---------|---------|---------|
| 🟢 **只读** | 仅读取文件、打印统计结果 | 可直接执行 |
| 🟡 **写入临时文件** | 写入 `/tmp/` 或当前项目的 `build/` | 说明路径后直接执行 |
| 🔴 **修改生产文件** | 删除、覆盖、移动用户工作目录下的文件 | **必须用户明确回复"确认执行"** |
| ⚫ **网络/系统级操作** | 调用外部 API、修改系统配置、安装软件 | **禁止自动执行，必须分步人工操作** |

### Step 3: 执行与清理
- 优先使用 `python3 -c "..."` 或写入临时脚本 `/tmp/kimi_ptc_$(date +%s).py` 后执行。
- 执行后，立即展示：
  - 退出码（是否为 0）
  - 标准输出（前 200 行，过多则截断并说明）
  - 标准错误（如有）
- 临时脚本默认保留 10 分钟后自动清理（由系统 `/tmp` 策略处理）。

### Step 4: 回退机制
如果脚本执行失败（非零退出码、输出异常、权限不足）：
1. 分析错误原因。
2. 尝试修复脚本后重新执行（仅限 🟢/🟡 级别）。
3. 若连续两次失败，**自动回退到传统单步工具调用**。

## 脚本模板

### Python 模板（数据处理）

```python
import os, json, glob, sys
from pathlib import Path

# 配置区
target_dir = "{path}"
pattern = "{pattern}"

# 执行区
results = []
for filepath in glob.glob(os.path.join(target_dir, pattern), recursive=True):
    # 你的处理逻辑
    results.append({"file": filepath, "value": ...})

# 输出区
for r in sorted(results, key=lambda x: x["value"], reverse=True):
    print(f"{r['value']}\t{r['file']}")
```

### Shell 模板（快速文件操作）

```bash
find "{path}" -name "{pattern}" | xargs wc -l | sort -rn
```

## 最佳实践

1. **保持脚本简洁**：脚本是"一次性胶水"，不是生产代码。10-30 行为宜。
2. **路径硬编码**：避免使用相对路径或环境变量，防止在工作目录变化时出错。
3. **输出结构化**：优先输出表格、JSON、Markdown 列表，便于直接引用。
4. **失败即回退**：不要在一个脚本上死磕。脚本失败不是丢脸的事，手动工具兜底才是 professionalism。
